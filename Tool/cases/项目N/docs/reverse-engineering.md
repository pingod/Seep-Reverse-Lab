# 项目N 离线许可信任锚替换与宽限期时间基准旁路（CWE-347 / CWE-602 / CWE-693）

> 受权范围白盒审计（G-Auth）。目标为已获书面授权的 Windows 桌面应用（本文称**项目N**，
> 版本记为 vN）。产品名、厂商域名、内置公钥字面值、设备指纹与本机标识已按仓库脱敏
> 规范屏蔽；地址级事实与判定语义保留，供方法论复现。
>
> 结论一句话：**该授权体系的密码学部分实现正确，信任锚与时间基准部分完全失效。**
>
> 运行时：Rust 原生 GUI（样本含 `rust-windowing/winit`、`Winit::ExecMsg`、`wgpu_core::*`、
> `WGPU_BACKEND` 等字符串），**不是** Tauri/WebView 架构（`tauri`/`webview2` 各 0 次出现），
> 单实例。授权判定全在原生侧，无 JS 层可 Hook——这也是本例走纯静态 + 原生插桩的原因。

## 一、授权链路总览

```
                 ┌──────────────── 启动 ────────────────┐
                 │                                      │
     license.ini │ （未签名明文缓存：55B 头 + 10 键）    │ license.sig
                 ▼                                      │ （已签名离线证明：103B 头 + 7 字段）
     [设备指纹比对]  ini.device_fp  vs  FNV-1a-64(MachineGuid)
                 │                                      │
        不匹配 → code=6                                 │
                 │                   （此步在验签之前：  │
                 │ 匹配                 两次 q0=6 时     │
                 ▼                    ed25519_verify     │
     [验签 Ed25519]  ◄──────────────────── 未被调用 ─────┘
        （内置公钥常量：.rdata，64 位十六进制 ASCII）
                 │
        失败 → code=4        （写入点静态定位，本次未动态采到）
                 │ 成功
                 ▼
     [宽限期判定] fill_result：now ≤ proof_date + 1209600 ？
                 │                        │
              是 → code=1               否 → code=2
            （离线授权有效）          （宽限已过）
                 │
                 ▼
     [在线复核]（每进程一次）POST /v1/accounts/<account>/licenses/actions/validate-key
                 │
        验签失败/不可信响应 → 记 WARN，**不降级**（fail-open）
```

判定输出是一个状态码 + 有效期/更新策略/死线的结果结构，UI 直接消费。

## 二、信任锚：验签是真执行的，但锚可就地替换

### 2.1 验签是否真的执行：动态证据与静态推得的边界

常见客户端是"验了不看返回"。本例不是。但**必须把动态采到的与静态推出来的分开陈述**：

**动态实测到的状态判别式**（Frida 读回结果结构首字 `q0`）：

| `q0` | 条件 | 命中 |
| :---: | :--- | :---: |
| 1 | 换锚 + 自签证明 + 指纹匹配 | 11 |
| 6 | 指纹带 `0x` 前缀 / 值不符（**先于**验签，这两次运行里 `ed25519_verify` 从未被调用） | 2 |
| 2 | `date` 头回拨 30 天 | 1 |

**验签点运行期命中记录**（两次独立运行，间隔约 14 分钟）：

```
[ed25519_verify] ret=<product>.exe+0x6d0877  sig=<sig ptr>  arg1=<key buf>  arg2=0x40
    arg1_as_hex64 = 33 38 31 30 61 31 30 66 31 63 64 37 36 39 66 64 …   ← ASCII
    -> 0xffffff01
```

`arg2 = 0x40`（64 字节）、`arg1` 的前 32 字节 ASCII 解出来正是**我们换进去的那把公钥的十六进制串前缀**
——⇒ 验签在每次启动的真实路径上被执行，且用的就是我们替换后的锚；不是死代码。

**静态推得、本次未动态采到**：`4`（证明缺失/验签失败）与 `0/3`（在线可信）。
`4` 的写入点定位在 `sub_1404A06F8` 尾部（`v112[0].m128i_i64[0] = 4;` 紧接
`sub_1404A4C45(v112)` 状态存储）；`0/3` 需要服务端正常应答，评估环境不可得。

另外**未**做"未换锚 + 同一份自签证明 ⇒ 被拒"的干净负对照：换锚前捕获到的两次失败
（`q0=6`）其实卡在**设备指纹**这一步，`ed25519_verify` 根本没被调用过，
因此不能拿来当"验签拒绝了自签证明"的证据。
⇒ "验签失败会真的导致未授权"是**反编译结论**（验签返回值参与状态写入），不是实测结论。
厂商复核时应先补齐这一档，再据此设计监控指标。

**因此本例没有走"patch 验签返回值 / 反转比较跳转"这条路**——
反编译显示验签结果被消费，那么更干净、且不破坏任何校验逻辑的路径就是把锚换掉后重签。
攻击面在锚，不在算法。

### 2.2 锚的物理形态

内置许可公钥以**明文十六进制 ASCII 常量**存在于 `.rdata`：

| 项 | 值 |
| :--- | :--- |
| 文件偏移 | `0xB98733` |
| 虚拟地址 | `0x140B99733`（imagebase `0x140000000`，`.rdata` VA→file delta `0x140001000`） |
| 长度 | 64 字节（= 32 字节 Ed25519 公钥的十六进制文本形态） |
| 引用点 | `0x1404A2296`、`0x1404A4A3E`、`0x1406A451A`、`0x1406D0845`（**单一常量、四处引用**） |

要点：

1. **等长**。替换前后都是 64 个 ASCII 字符，不改节表、不改任何偏移表、不需重定位、不破坏 PE 结构。
   整个补丁的改动跨度就是这 64 字节（其中 60 字节实际不同）。
2. **明文**。不需要从 DER/PEM 里剥模数，静态搜索 64 位十六进制串即命中。
3. **单点**。四处引用同一个对象 ⇒ 一次替换覆盖全部使用点，无冗余副本需同步。
4. 同一区域另有一个同形状的公钥常量（`0x140B998DD`），用于**插件签名**路径，与许可判定无关；
   搜索时须按引用点区分，勿误替换。

### 2.3 替换后即可自签

持有任何自签 Ed25519 密钥对，都能产出结构完全合法、客户端判定可信的离线证明。
证明格式（`license.sig`）：

```
# <product> license proof …            ← 103 字节模板，取自 .rdata @0x140BA72DF
schema = 1
host = <vendor-host>
path = /v1/accounts/<vendor-account>/licenses/actions/validate-key
date = <RFC1123 GMT>
digest = sha-256=<b64(sha256(body))>
signature = algorithm="ed25519",signature="<b64>",headers="host date digest"
body_b64 = <b64(JSON)>
```

签名基串严格按 `headers` 顺序拼接：

```
host: <vendor-host>\n
date: <RFC1123 GMT>\n
digest: sha-256=<b64>
```

即"HTTP 消息头签名"（RFC 9421 风格）的离线落盘版。

## 三、时间基准：宽限死线锚在"我们自己签的那个日期"上

这是本例最有方法论价值的一段。**三个候选锚点，两个是错的，且错的方向不同。**

### 3.1 假设演化

| # | 假设 | 实验设计 | 结果 |
| :--- | :--- | :--- | :--- |
| T1 | 死线 = `license.ini` 的 `last_validated + 14d` | `--lv-offset-days +30` | ❌ 推翻：UI 剩余天数**不变** |
| T2 | 死线 = `license.ini` 的 `activated + 14d` | `--act-offset-days +30` | ❌ 推翻：UI 剩余天数**不变** |
| T3 | 死线 = `license.sig` 已签名 `date` 头 `+ 14d` | `--sig-date-offset-days +30` | ✅ 命中：剩余天数 **1:1** 外推 |

T1/T2 之所以看似合理：`last_validated` 字面义即"最近一次验证"，且确实每周期被更新——
它是**显示字段**，不是判定输入。若不区分，就会去加固一个不参与判定的字段。

### 3.2 关键对照：排除"许可证变化导致重算"的干扰

T1/T2 的实验里换了 license key 与 uuid，可能被解释成"新许可证 ⇒ 重新计时"。
因此补做**同许可证重放对照**：保持 license key / uuid / install_id / body 全同，
只改一个日期来源再重启进程。结果——

- 只改 ini 的 `last_validated` / `activated` → 剩余天数不动；
- 只改 `license.sig` 的 `date` 头（并重新签名）→ 剩余天数同步移动。

这排除了"许可证身份变化触发重新计时"的解释，锚点唯一确定。

### 3.3 判定代码（`fill_result` @ `0x1406F02C0`）

```c
unsigned __int64 __fastcall sub_1406F02C0(__int64 a1, __int64 a2, __int64 a3)
{
  result = sub_1406F0349(a1, a2, a3);              // maybe_time() -> now(epoch seconds)
  v6 = *(_BYTE *)(a2 + 128);                       // updates 判别式
  v7 = *(_QWORD *)(a2 + 96);                       // expiration
  if ( v6 == 3 && v7 != 0 && result > v7 ) {       // 仅 updates==3 时看过期
    result = sub_14000902E(a1 + 8, aExpired_0, 7);
    *(_QWORD *)a1 = 6;                             // code=6
  } else {
    v8 = -1;
    if ( *(_QWORD *)(a2 + 104) < 0xFFFFFFFFFFED8B00uLL )
      v8 = *(_QWORD *)(a2 + 104) + 1209600LL;      // ← 死线 = proof_date + 14d
    if ( result <= v8 ) {
      result = v7 != 0;
      *(_QWORD *)a1 = result;                      // code=1（离线有效）
      *(_QWORD *)(a1 + 8)  = v7;
      *(_BYTE *)(a1 + 16) = v6;
      *(_QWORD *)(a1 + 24) = v8;
    } else {
      *(_QWORD *)a1 = 2;                           // code=2（宽限已过）
    }
  }
  return result;
}
```

`0x127500`（=1209600）在**整个二进制里只出现一次**（`0x1406F030B`，`.text`），
这既是定位锚，也说明不存在第二个宽限路径。

`maybe_time` @ `0x1406F0349`：

```c
v2 = (hi << 32) | GetSystemTimeAsFileTime_low();
result = (v2 - 116444736000000000LL) / 0x989680uLL;   // FILETIME -> epoch 秒
```

即**直接取本地系统时钟**，无单调时钟、无防回滚存储。

### 3.4 双向利用

| 方向 | `--sig-date-offset-days` | 实测 |
| :--- | ---: | :--- |
| 前推（延长） | `+3650` | 死线推到约十年后；断网长期保持 `code=1` |
| 回拨（反向对照） | `-30` | `fill_result` 输出 `02 00 00 00…`，`code=2`，UI 显示宽限已过 |

**无时效/偏差校验（no skew check）**——客户端不问"这个日期是不是来自未来"。
反向对照的意义：只有正方向命中可能是巧合（例如"任何日期都能过"），
双方向 1:1 跟随才证明该字段**确实**是死线的唯一自变量。

## 四、设备指纹：无密钥哈希，明文可比对

| 项 | 内容 |
| :--- | :--- |
| 推导 | `sub_1404A2108`：`FNV-1a-64( MachineGuid 字符串 )`，取小写十六进制，16 字符 |
| 来源 | `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` |
| 比较 | `sub_140008885`，**逐字节严格相等** |
| 失败 | `code=6`，且发生在**验签之前** |

三点要害：

1. **无密钥**。FNV-1a 是非密码学哈希，公开常量初始化，任何人可本地复算 ⇒ 不构成绑定，只是"可算出的常量"。
2. **明文存储**。指纹同时写进未签名的 `license.ini`（`device_fp`），比对双方都在攻击者手里。
3. **格式即门控**。带 `0x` 前缀、大写、长度不符都会失败——实测一次因为前缀直接 `device_mismatch`。

（本案例归档不包含真实 MachineGuid 与真实指纹；`src/keygen.py` 在运行时从本机注册表实时派生，
不硬编码任何具体值。）

## 五、`updates` 策略与"过期字段根本不参与判定"的分支

`sub_1404A60EB` 把字符串映射为判别式：

| 字符串 | 判别式 | UI 标签（实测） |
| :--- | :---: | :--- |
| `strict` | 0 | 按版本回退 · 更新有效期至 {date} |
| `rollback` | 1 | （按标签表顺序推定，未实测） |
| `lifetime` | 2 | 永久更新 |
| 其它 | 3 | — |

回到 §3.3 的代码：**过期检查是 `v6 == 3` 守卫的**。也就是说：

- `updates = lifetime`（2）⇒ `expiration` **完全不参与判定**，有效期写什么都行（F-06）；
- 只有落到"其它"（3）这个兜底值，有效期才开始裁决。

这是一个典型的"策略字段与时间字段耦合"缺陷：把最宽松的策略值同时设为**跳过时间校验**的开关。

## 六、在线复核 fail-open

| 项 | 内容 |
| :--- | :--- |
| 任务体 | `0x1404A06F8` |
| 引擎 | `0x1404A21C8`（5125 字节大函数） |
| 触发 | 每进程一次，`byte_140D43DBB` 做已执行门闩 |
| 端点 | `POST /v1/accounts/<vendor-account>/licenses/actions/validate-key` |

实测：服务端不可达、或服务端返回**验签失败**的响应时，客户端只记录一条
`[WARN] … untrusted reply (signature verification failed …)`，
**本地授权状态不变**。断网、MITM、服务端吊销均不撤回已获得的状态。

这使 F-01 + F-02 的效果变成**不可撤回**：一旦写入，服务端没有正常手段收回。

## 七、漏洞定级

| 编号 | 发现 | 类别 | 分级 | 状态 |
| :--- | :--- | :--- | :---: | :--- |
| **F-01** | 内置 Ed25519 公钥为可等长就地替换的明文常量，替换后可自签离线许可 | CWE-347 / CWE-1188（信任锚的不安全默认） | **严重** | 确认利用 |
| **F-02** | 离线宽限死线锚定在**自签证明的 `date` 头**，且无时效校验，前推即永久授权 | CWE-602 / CWE-693 | **高** | 确认利用 |
| **F-03** | 在线复核返回不可信时不降级（fail-open），状态无法撤回 | CWE-693 | 中 | 确认利用 |
| **F-04** | 设备指纹 = 无密钥 FNV-1a-64(MachineGuid)，本地可比对且存于未签名文件 | CWE-325 / CWE-345 | 中 | 确认利用 |
| **F-05** | `license.ini` 为未签名明文缓存，10 个授权字段全部可篡改 | CWE-345 | 中 | 确认利用 |
| **F-06** | `updates=lifetime` 路径下 `expiration` 不参与任何判定 | CWE-639 变体（策略短路） | 低 | 确认利用 |
| **F-07** | 状态机存在冗余信任输入与"时间语义重载"（显示字段与判定字段混淆） | 现象 | 信息 | 观察 |

### 攻击链（五步，全部本地，无需服务端配合）

1. 取得目标 exe 的写权限（用户目录下的安装位置即可写）；
2. 在偏移 `0xB98733` 等长替换 64 字节公钥为自己持有的 Ed25519 公钥；
3. 按 §2.3 的签名基串格式自签 `license.sig`，`date` 头前推；
4. 写 `license.ini`：`device_fp` 用本机 MachineGuid 现场复算，`updates = lifetime`；
5. 断网启动 ⇒ `code=1`，UI 完整解锁，宽限期显示为剩余约十年。

**叠加效果：永久、离线、可绑定任意设备指纹，且服务端无法通过正常吊销手段撤回。**

## 八、已被实测推翻的假设（请勿据早期草稿整改）

| # | 早期结论 | 实测 | 若照此整改的后果 |
| :--- | :--- | :--- | :--- |
| R-1 | 宽限期锚在 `last_validated` | ❌ 错，该字段仅显示 | 加固一个不参与判定的字段，攻击面不变 |
| R-2 | 宽限期锚在 `activated` | ❌ 错，同上 | 同上 |
| R-3 | "验签失败会降级本地状态" | ❌ 错，fail-open 只记 WARN | 以为断网即失效，忽略离线证明的主路径 |
| R-4 | "客户端会重写 `license.ini`" | ❌ 错，下发后从未被重写（部署件与生成件逐字节相同） | 误判 ini 为受管控存储，实际是完全攻击者可控的缓存 |

> **净效果**：R-1/R-2 指向的字段加固无效；真正的锚在**已签名证明**里，
> 而那份证明的签名密钥已经被 F-01 换成了攻击者的。

## 九、方法论要点（可迁移）

| # | 要点 | 本例的教训 |
| :--- | :--- | :--- |
| M-1 | 插桩前先结束既有进程 | 目标是**单实例**应用。另起一个实例会被转发给主实例后退出，Frida trace 全零。第一次"零命中"极易误判成"函数没执行" |
| M-2 | 字符串比对要先确认其严格性 | `device_fp` 逐字节相等 ⇒ `0x` 前缀、大小写、长度都会失败。别把"格式错"当"逻辑错" |
| M-3 | 时间锚点必须用**同许可证重放**来判别 | 只改日期又同时换了 license id，会把"重新计时"误读成"锚点命中" |
| M-4 | 证据管道禁止 `head` | `… \| head -40` 触发 SIGPIPE，被采进程可能中途退出，产生假阴性 |
| M-5 | 每个引用地址都要回到证据核对 | 附录地址表若含未核对值，必须删除而非保留。"看起来合理"的地址比没有地址更有害 |
| M-6 | 双向对照 | 正向命中 + 反向（回拨 ⇒ `code=2`）共同构成因果，单正向不足 |

## 十、加固建议（厂商侧）

### P0 — 下一版本

| 编号 | 建议 | 对应 |
| :--- | :--- | :--- |
| P0-1 | **信任锚不可就地替换**：公钥改存为带完整性校验的形式（与代码签名/其他节一起进哈希覆盖，或加密后运行期解出，或多锚点冗余+一致性判定）；单点等长可替换常量等于没有信任锚 | F-01 |
| P0-2 | **宽限期不得以自签材料内的日期为锚**：改为防回滚单调时钟（加密存储的"最高水位线"，且该水位参与判定），或要求带服务端签名的时间戳 | F-02 |
| P0-3 | **对已签名证明施加时效校验**：`\|proof_date − now\|` 超过阈值即拒绝；未来日期直接拒绝 | F-02 |

### P1 — 后续版本

| 编号 | 建议 | 对应 |
| :--- | :--- | :--- |
| P1-1 | 在线复核不可信/失败时应**降级**并给出明确提示，而非静默 fail-open | F-03 |
| P1-2 | 设备绑定使用服务端持有的密钥做 HMAC/AEAD，或改用硬件信任根；无密钥哈希不是绑定 | F-04 |
| P1-3 | `license.ini` 全部字段进入签名覆盖范围（或直接删除该缓存），消除"未签名明文信任输入" | F-05 |

### P2 — 持续改进

| 编号 | 建议 | 对应 |
| :--- | :--- | :--- |
| P2-1 | 策略字段与时间校验解耦：`lifetime` 不应同时意味着"跳过过期判定" | F-06 |
| P2-2 | 敏感能力后端化，前端状态不作为特权操作的唯一凭据 | 整体 |
